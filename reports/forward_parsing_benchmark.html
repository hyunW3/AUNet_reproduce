AU-Net · model forward + parsing benchmark

What actually costs time in a byte-model step

Six 100M models, matched on compute params. The transformer forward is nearly identical across the byte family — the real spread is in boundary computation: cheap for regex/trie parsers, model-side (in the forward) for byteflow, and dominated by the entropy LM for BLT. fp16 tames the last one.

Parameter budget · llama vs byte

Matched on non-embed params — not the same shape

The two models carry the same ~99 M compute (non-embedding) parameters, but spend them differently, and their trunks are not identical. llama’s 3× larger total is entirely its 128k-vocab embeddings (compute-free lookups), which is why the fair match is on non-embed params.

Trunks: same layer, different depth

Both use the identical dim-768 block (7,079,424 params/layer), but the byte trunk is 10 layers and llama is 14. The byte model trades ~4 dim-768 layers (~28 M) for a dim-512 encoder + decoder + transitions (~28 M) — same budget, different shape.

Match params or FLOPs/byte?

Different questions. iso-param controls capacity but lets the byte model spend 2.2× the compute/byte; iso-FLOPs/byte controls what you pay and pairs with BPB — the more defensible axis for byte-vs-subword. Even FLOPs isn’t the last word: wall-clock here is only ~1.4× (not 2.2×), because the byte model’s MFU is higher (21.8% vs 13.5%).

Why FLOPs/byte differs: llama amortizes all 99 M params over 4.541 bytes/token; the byte model amortizes only its 70.8 M trunk over patches but runs its 27.5 M local layers (encoder+decoder+transitions) on every byte — that un-amortized per-byte compute is the 2.2×.

Proposed · not yet measured

What a compute-matched (iso-FLOP) comparison would take

Everything above is iso-param. The fairer test equalizes FLOPs/byte and compares BPB (bits/byte). The catch: at equal compute/byte, llama carries ~2.4× more parameters than the byte model — so the real question becomes “does byte-level representation beat having 2.4× fewer weights at the same compute?” That needs training runs, not just the measurements in this report.

What’s required to run it

  • Train each family at ≥3 sizes on the same data, logging total training FLOPs (a compute-frontier, not one point).
  • Evaluate BPB on a common held-out byte stream — the only tokenizer-independent metric; never per-token perplexity.
  • Match total training compute (FLOPs/byte × bytes seen), ideally Chinchilla-optimal params/data per point; per-model-tuned HP; ≥2 seeds + CIs.
  • Plot BPB vs training-FLOPs; the lower frontier wins. This slots straight into the existing root_greedy compute-frontier — just add llama points to the same axes.
  • Optionally also throughput-matched, since wall-clock ≠ FLOPs (byte MFU is higher).

When iso-param is the right axis (and when it isn’t)

iso-param answers capacity/representational questions and static memory footprint — legitimate, but it hides this ~1.9× training-compute gap and doesn’t help at inference (byte models emit ~4.5× more decode steps per unit text). For a training-compute or BPB-per-FLOP comparison, iso-FLOP / compute-frontier is the defensible axis; iso-param is a secondary lens. Note the “iso-param” here already excludes embeddings — itself a compute-motivated choice, so it’s really iso-compute-param.

hybrid-bt: 38% cheaper, verified equivalent

Parsing the prefill region with a byte-trie (longest-match) instead of real-BPE drops hybrid from 0.308 → 0.192 ms/KB — it skips the UTF-8 decode + map_codepoint_to_byte and the tiktoken offset call. The patch-length distribution is statistically identical (bytes/patch 4.575 vs 4.570; matching p50/p90/p99; 12% byte-fallback), it’s deterministic, and every doc tiles validly — a one-line bpe_hybrid_prefill: bt flip.

BLT’s entropy parser is off this chart

The entropy LM costs 2.47 ms/KB on GPU (fp16) — ~8× the priciest regex/BPE parser — and ~1700 ms/KB on CPU. That CPU cost is why BLT training uses Option-A: move the parser onto the GPU, batched, in the training step.

Why hybrid is the priciest: it runs two parsers per document — real-BPE on the prefill region (_bpe_end_offsets, ~56% of the time) and the greedy byte-trie on the decode region (~30%) — plus md5 sampling, a UTF-8 decode, and set/loop merge bookkeeping. hybrid-bt removes the real-BPE half. byteflow’s real boundaries come from the model-side lossy coding-rate calc (in the forward, ~0.3 ms), so its 0.226 above is only the discardable word placeholder.

Removing the violet group (56%) is exactly what hybrid-bt does — it trades the real-BPE prefill for a byte-trie one, at ~2.2× lower prefill cost, which is why the total drops 0.308 → 0.192 ms/KB.

Two things these numbers don’t depend on — and one they do

Boundary sampling is free: the actual leaderboard models sample the prefill/decode split with uniform_mid (N/3–2N/3), not uniform_full (0–N) — but both average the split at ~N/2, so parsing cost is identical (leaf 0.550 vs 0.561, bt 0.331 vs 0.330 ms/KB; <2%). The bt-prefill saving (~40%) holds on the exact uniform_mid models. But absolute ms/KB is CPU-bound: parsing runs on the host CPU, so the scale shifts with the machine — the same configs profiled ~1.7× higher on the A100 host than on the B200 host used for this chart (every builder scaled uniformly). The relative ordering and the bt-vs-leaf ratio are portable; the absolute values are not.

Centerpiece · why BLT was slow

The entropy model ran in fp32 — that was the whole cost

fp32 does two expensive things at once: it forgoes the tensor cores (fp32 matmul ≈ 19.5 vs bf16 ≈ 312 TFLOP/s on A100) and it disables the flash / memory-efficient SDPA kernel — fp16/bf16-only — so attention falls back to the O(n²) math path over 8192 tokens. Lowering precision fixes both.

Why fp16 over bf16 here

Both hit the tensor cores and flash-SDPA, so both land near 79 ms. But fp16 keeps 10 mantissa bits vs bf16’s 7, so entropy values near the threshold survive rounding — 10× fewer boundary flips (0.02% vs 0.20%), total boundary count off by just −2 of 4725. fp16 captures the speed and nearly all the fp32 boundaries.

Shipped · code change

An entropy_dtype option, defaulting to fp16

The precision is now configurable and wired through the production paths. fp16 is the main default; fp32 stays one flag away for exact-boundary reproduction.

# apps/aunet/data/regex_cutting.py — RegexArgs
entropy_dtype: str = "fp16"   # "fp16" (default, ~5× faster, ~0.02% flips)
                          # | "bf16" (~0.2% flips) | "fp32" (exact, ~5× slower)

# plumbed to the GPU paths that run the entropy model:
train.py            # Option-A step:  EntropyModel(..., dtype=_rx.entropy_dtype)
regex_cutting.py    # eval GPU path:  EntropyModel(..., dtype=self.entropy_dtype)
EntropyModel        # cast AFTER building RoPE in fp32; CPU is forced back to fp32

Recommended setup

Run Option-A training and the eval/GPU boundary path in fp16 — same code, so boundaries stay self-consistent and you get the 5× across the board.

Two things to watch

The CPU / offline-precompute path stays fp32, so mixing it with fp16 training reintroduces the 0.02% mismatch — keep one precision end-to-end. fp16’s narrower range was fine on this 50M model; re-check on larger entropy models.

Method & caveats

How these were measured

  • Forward: standalone bench_model_forward builds the real model on one GPU with synthetic byte batches; forward-only timed with CUDA events after warmup. Not torch.compiled — real training compiles, so live latency is lower; these are apples-to-apples eager numbers.
  • FLOPs/byte: model.flops_per_token() (the 6·N·D figure the loop logs as speed/FLOPS). Byte models: 1 token = 1 byte. llama: divided by 4.541 bytes/token measured on the eval shard.
  • Parsing: bench_data_processing times tokenizer.encode plus each RegexPool level_mask builder per document, reported per KB. Entropy parsing is entropy_level_mask_gpu (Option-A GPU) or the per-seq CPU patcher.
  • Entropy precision: softmax/entropy always in fp32; only the transformer downcast. Boundary flips compared against the fp32 mask on identical input.
  • The byte variants (aunet-word, bpebyte, hybrid, byteflow, BLT) share the [512,768]/[3,10] backbone, so their forwards match within 0.5% — every real difference between them lives in the parser, measured above.
